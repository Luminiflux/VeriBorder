- thickness 0.8 px, frame 0.8 px dark metal, pane 0.5 px -> 
  0.15 px shadow recess behind each frame face;
- leaves are 5.35 px long and stop 0.05 px short of the centre line, leaving a 0.1 px gap at x = 8;
- front hinge z = 2.2 (leaf 1.8..2.6), rear hinge z = 14.2 (leaf 13.8..14.6);
- **clear gap 11.2 px = 0.7 block (0.7 格)** between the closed leaves.
  This is a GAMEPLAY constant, not styling: the player is 0.6 blocks wide and must be
  able to stand inside the chamber for the two-stage "crossed the middle" logic to fire.
  11.2 px = 0.700 block leaves 0.1 block of slack. The generator
  asserts `clear >= 11.2` and refuses to build below it, so this cannot silently regress.
- derived rear hinge: 2.2 + 0.8 + 11.2 = 14.2;
- both leaf pairs stay inside the block: z 1.8..14.6, i.e. 1.8 px clear of z=0 and 1.4 px clear of z=16;
- leaves span x 2.6..13.4, exactly the lane, so they never
  enter the cabinet skins (x 0..2.6 / 13.4..16).
- each group origin sits exactly on its hinge, so a Y rotation in Blockbench or in Java
  swings the leaf without any offset maths;
- open: +-95 deg about Y, so each leaf folds back flat onto its own cabinet inner face.

Every cap element name is prefixed `cap_left_*` / `cap_right_*`. They form the outer
0.2 px skin of each cabinet plus the outer lid lip. The outermost 1 px (x 0..1 and
15..16) carries no trim, LED or chamfer, so two gates placed side by side meet on a
flat plane. Cap segments leave module seams that stay visible when the gates are
joined: 0.2 px at y = 1.2 (kick line), 0.4 px at y = 8.4 (service-hatch split),
0.15 px at y = 13.2 (panel joint). Each seam exposes the core 0.2 px deeper, so a run
of gates reads as bolted modules rather than one extruded slab.

### Tablet alpha repair (round 2)

`egate_tablet.png`, `exit_gate_tablet.png`, `dual_gate_tablet.png` were the only
gate screen textures with a feathered alpha channel: a baked drop shadow at alpha 13
(3195 px) / 38 (300) / 97 (232) / 85 (60) / 114 (20) / 144 (4) over the 285 px green
"verified" glyph. **3811 px per file, 11433 px total**, were forced to alpha 255 with
the colour channel untouched, so the shadow became a colour ramp instead of
transparency (the alternative, thresholding to transparent, would have deleted 93%
of the panel). Reproduce with `node tools/fix_texture_alpha.js --fix --opaque`; the
tool only touches non-`_glass`/`_leaf` textures, because those are translucent by
design on their own render layer.

### UV convention (16 vs 32 vs 64)

Minecraft block-model UVs are **normalised to 0..16 no matter the PNG size**: a face
that covers a whole 32x32 or 64x64 texture is still `[0,0,16,16]`. Growing a texture
from 16 to 32/64 therefore needs **no** UV change - MC rescales internally, and
`tools/preview_models.js` does the same (`u/16*tex.w`). Sub-rects stay in 0..16 too:
the screen plate is square (1.80 x 2.00 px), so it samples the whole 64x64 UI with
`uv [0,0,16,16]` and is displayed 1:1 instead of squashed; the small console display
samples the 64x14 status strip with `uv [0,11,16,15]` (rows 44..57 of 64).

## 6. Block models + blockstates

Four model files per gate, all sharing one element list:

- `block/<id>.json` - both caps present
- `block/<id>_left.json` - `cap_left_*` removed
- `block/<id>_right.json` - `cap_right_*` removed
- `block/<id>_both.json` - both removed

`blockstates/<id>.json` has 4 facings x left x right x open = **32 variants**, keyed
`facing=<dir>,left=<bool>,right=<bool>,open=<bool>`. `open` maps both values to the
same model - the leaves belong to `EGateRenderer`, the model has no door geometry.
The properties must exist on the block in Java (`DeviceBlock.LEFT` / `RIGHT` as
`BooleanProperty`); until they are declared, vanilla will reject these variant keys.

## 7. Validator changes made in round 1-2

`tools/preview_models.js` carried limits from the previous (16 px tall, 3 px cabinet)
generation that contradict this spec. They were updated, not bypassed:

1. gate height bound `y <= 20.0` -> `y <= 22.5` (camera head reaches y = 21.45);
2. gate clear box `x 2.9..13.1, y <= 23` -> `x 2.6..13.4, y <= 17.5`: cabinets end on
   2.6/13.4 as specified, and the cantilevered head above the door frame is allowed
   (nothing below 17.5 px intrudes, which is all the walkable lane needs - the door
   leaves are 12 px tall);
3. element rotation had to be a multiple of 22.5 deg -> any multiple of 2.5 deg
   (<= 45), because the reader deck and the camera screen are 15 deg slants while
   `station_verifier` keeps its legacy 22.5 deg steps;
4. the "exactly 22 block models" assertion is gone. It would have failed the moment a
   gate grew variants. Every json is now validated on its own merits (elements, bounds,
   texture resolution, palette, size) and a required-id list is checked instead, so the
   count may grow while each model still has to pass every rule;
5. the gate blockstate check expects the 4-property key format instead of
   `facing=...,open=...`.

Two other tool changes:

- `tools/bbmodel_to_mc.js` exports `convert(raw, id, opts)` (the generator and the
  variants share one code path) and writes compact JSON by default (`--pretty` keeps
  the readable form);
- `preview_models.js` renders `assets/models/_preview/*_{assembly,pair,seam}.json` with
  no validation attached, so the shipped models keep the strict passage rule while the
  closed wings and the joined pair stay reviewable.
